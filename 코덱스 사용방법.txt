🔥 한 줄 결론

코덱스는 “질문”이 아니라 “작업 지시서”로 움직인다.

1️⃣ 작업 단위부터 잘라라 (이게 70%다)
❌ 망하는 방식

“채팅 기능 전체 만들어줘”

👉 너무 큼 → 품질 흔들림 → 다시 뜯음

✅ 정답

“기능 단위”로 쪼갠다

예:

채팅 메시지 저장 API
메시지 시간 표시 로직
방별 메시지 분리 구조
실시간 구독 처리

👉 하나씩 “완결”되게

2️⃣ 지시 구조 (이대로 쓰면 된다)

코덱스한테 이렇게 던져라:

[목표]
채팅 메시지 시간 표시를 방별로 독립적으로 나오게 수정

[현재 상황]
- 모든 채팅방에서 lastMessageTime 공유됨
- 그래서 다른 방에서도 시간 표시 안 나옴

[요구사항]
- 채팅방별로 lastMessageTime 따로 관리
- 기존 UI 구조 유지
- 최소 수정

[코드]
(여기 전체 코드 붙임)

👉 이게 핵심이다

3️⃣ 프롬프트 공식 (외워라 그냥)

목표 → 현재 문제 → 요구사항 → 코드

이 순서 안 지키면
👉 토큰 낭비 + 결과 불안정

4️⃣ 결과 받으면 이렇게 써라
❌ 바로 다음 질문

→ 토큰 낭비 루프

✅ 정석 흐름
코드 적용
테스트
문제만 다시 요청

예:

“이 부분에서 null 에러 발생, 이 함수만 수정해줘”

👉 점점 정밀하게

5️⃣ 리팩토링 요청 방식 (고급)

이건 진짜 중요하다

❌

“코드 깔끔하게 해줘”

👉 의미 없음

✅
[목표]
코드 가독성 개선

[제약]
- 기능 변경 금지
- 변수명 명확화
- 중복 제거

[코드]
...
6️⃣ 서버 작업 시 필수 구조

예:

[목표]
검증 코드 생성 API 구현

[요구사항]
- 6자리 랜덤 코드 생성
- 3분 후 만료
- DB 저장
- 중복 방지

[환경]
Node.js + Express

[출력]
- API 코드
- DB 스키마

👉 이렇게 주면 바로 실전 코드 나온다

7️⃣ 절대 하지 마라 (진짜 중요)
❌ 감정형 질문

“이거 왜 안 되냐?”

❌ 코드 없이 질문

→ AI 추측 → 틀림 → 반복

❌ 한 줄씩 계속 요청

→ 토큰 박살

8️⃣ 현실적인 운영 방식 (이게 핵심 루틴)

하루 작업 기준:

기능 하나 정의
코덱스에 “작업 지시서” 전달
코드 받기
테스트
오류만 다시 요청

👉 이걸 반복

🧠 핵심 한 줄

“코덱스는 질문에 답하는 게 아니라
지시를 수행한다.”
